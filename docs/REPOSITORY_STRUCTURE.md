# Структура репозитория HarvestHub

Этот файл фиксирует единую схему размещения кода. Новые файлы должны добавляться в существующие разделы, а не рядом с ними в параллельные папки.

## Основные каталоги

- `js/core/` — загрузка приложения, навигация, тема, локальное хранилище и общая инфраструктура.
- `js/ui/` — переиспользуемые элементы интерфейса и обработчики общего назначения.
- `js/pages/` — код конкретных страниц. Общая логика не должна оставаться здесь.
- `js/alliance/` — API и общие функции штаба союза.
- `js/sync/` — синхронизация локальных и облачных данных.
- `js/calculators/`, `js/season/`, `js/troop-training/`, `js/turbo-vs/`, `js/ipk/` — предметные модули калькуляторов.
- `css/` — общие и предметные стили. Одинаковые правила не должны копироваться между страницами.
- `pages/` — HTML-фрагменты страниц.
- `supabase/migrations/` — единственный каталог для новых изменений базы данных.
- `supabase/functions/` — Edge Functions.
- `scripts/` — проверки и служебные скрипты проекта.

## Правила для JavaScript

1. Перед созданием нового модуля проверять существующие `core`, `ui` и предметные каталоги.
2. Не добавлять глобальные обработчики, которые невозможно снять при переходе между страницами.
3. Страничный модуль обязан предоставлять понятный способ очистки созданных обработчиков, таймеров и наблюдателей.
4. Работа с Supabase должна идти через существующий предметный API-модуль, а не напрямую из разметки или обработчика кнопки.
5. Пользовательские строки выводятся через безопасное текстовое API (`textContent` или общий экранирующий помощник), а не через сборку HTML.

## Правила для CSS

1. Сначала расширять существующий общий класс.
2. Не создавать два класса с одинаковым набором правил для разных страниц.
3. Не помещать стили в HTML.
4. Адаптивные правила группировать с существующими правилами соответствующего компонента.

## Правила для Supabase

1. Новые изменения создаются только как миграции в `supabase/migrations/`.
2. Нумерация миграций должна быть уникальной и содержать дату и время.
3. SQL-файлы в корне `supabase/` считаются историческими снимками. Их нельзя расширять новыми изменениями.
4. Любая новая RPC-функция добавляется в `supabase/rpc-manifest.json`.
5. Для таблиц в открытых схемах обязательно проверяются RLS, политики и права ролей.
6. Для `SECURITY DEFINER` явно задаются `search_path`, проверки пользователя и разрешённые роли.
7. После изменения базы запускаются security- и performance-advisors Supabase.

## Проверка перед публикацией

Запустить:

```bash
npm run check
```

Та же проверка выполняется автоматически в GitHub Actions для основных и рабочих веток.
