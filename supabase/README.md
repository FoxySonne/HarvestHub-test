# Supabase в HarvestHub

## Единственный источник новых изменений

Все новые изменения базы данных должны находиться в `supabase/migrations/` и иметь уникальное имя вида:

```text
YYYYMMDDHHMMSS_short_description.sql
```

SQL-файлы, которые лежат непосредственно в `supabase/`, являются историческими этапами разработки. Они сохранены только для сверки старой схемы и не должны применяться вручную к действующей базе.

Полный перечень этих замороженных файлов находится в `legacy-sql-manifest.json`. Команда `npm run check` не позволит незаметно добавить в корень `supabase/` новый SQL-файл: новое изменение обязательно должно оформляться миграцией.

Крупные миграции не разбиваются задним числом, поскольку изменение уже применённой истории может привести к расхождению между репозиторием и действующей базой.

## RPC

Публичные функции, вызываемые клиентом, перечислены в `rpc-manifest.json`. При добавлении, переименовании или удалении RPC необходимо одновременно обновить этот файл.

Для каждой RPC проверяются:

- допустимая роль вызова;
- проверка `auth.uid()`;
- принадлежность данных пользователю или союзу;
- явный `search_path` для `SECURITY DEFINER`;
- отсутствие доступа `PUBLIC`, если функция не предназначена для гостей;
- атомарность массовых операций.

## Таблицы и RLS

Для таблиц в открытой схеме обязательны:

- включённый RLS;
- отдельные политики чтения и изменения;
- `USING` и `WITH CHECK` для обновления;
- ограничения целостности на уровне базы, а не только в интерфейсе;
- индексы для полей, используемых в связях, фильтрации и очистке архива.

Таблицы в `private` не выдаются клиентским ролям. Отсутствие пользовательских RLS-политик для них допустимо, если доступ выполняется только через проверенные серверные функции.

## Порядок изменения базы

1. Проверить существующие таблицы, функции и миграции.
2. Расширить существующий механизм вместо создания параллельного.
3. Сделать изменение атомарным и повторно применяемым там, где это возможно.
4. Добавить миграцию в `supabase/migrations/`.
5. Обновить `rpc-manifest.json`, если менялись RPC.
6. Запустить `npm run check`.
7. Проверить security- и performance-advisors Supabase.
8. Проверить результат отдельным запросом до слияния.

## Текущее предупреждение

В действующей базе есть много намеренно вызываемых клиентом функций `SECURITY DEFINER`. Сам по себе этот признак не означает ошибку, но каждая такая функция должна содержать собственную проверку прав. Массово отзывать `EXECUTE` или переводить функции в `SECURITY INVOKER` без проверки нельзя: это остановит работающие страницы сайта.
